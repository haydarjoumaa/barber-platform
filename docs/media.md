# Local shop galleries, logos and client photos

Owners can upload a shop logo and public gallery photos from separate workspace panels and profile/haircut photos from a client profile. Signed-in clients can upload or remove their own profile/haircut photos from their account. Each upload requires an explicit consent acknowledgment; owner uploads record the acting owner and confirmation of client consent. Consent timestamps and upload/removal events are retained. Barber and receptionist photo access is not granted by appointment permissions.

The logo and explicitly uploaded gallery photos of an active, published shop are public. Gallery images use `/{shopSlug}/gallery/{assetId}` and require the asset to belong to that shop, have the `SHOP_GALLERY` kind, and remain active. Unpublished, suspended or deleted shops do not serve gallery images. Client images require a live owner session for that shop or the matching shop-specific client session. Image endpoints return no-store responses (with private cache controls for authenticated client images) and bypass public image optimization. Client photos are not storefront or marketing images. Removing a photo withdraws access immediately through its database record; the application then attempts physical deletion. Replacement retires the previous logo or profile photo. Haircut photos form a private paginated gallery. Public shop galleries use a separate category, require permission to publish and consent from identifiable people, accept optional descriptions up to 200 characters, and show 12 photos per page, newest first. Descriptions are escaped text and serve as image alt text. Public uploads never replace the logo or publish an existing private client photo.

Uploads accept static JPEG, PNG or WebP up to 8 MiB and 20 million decoded pixels. The server checks decoded format against the declared type, rejects animation, applies orientation, resizes inside 1600 × 1600 and re-encodes as JPEG. Input metadata, including EXIF/GPS, is discarded; transparency becomes white. At most two conversions run simultaneously per application process. Authenticated upload attempts are rate limited. Original filenames are never storage paths.

## Storage and migration

Run `npm run db:deploy` and `npm run db:generate` before starting the apps. The original media migration adds tenant-scoped records, consent metadata and partial unique constraints for active logos/profile photos. `20261111000100_shop_gallery_kind` adds the gallery enum value; `20261111000200_shop_gallery_profile` updates the database subject constraint and adds captions and profile links. The enum is committed separately before its first use. All 20 migrations are applied locally as of November 11.

The shared `@barber/storage` package exposes an object-storage interface with a local filesystem implementation. By default both app workspace directories resolve to the repository's ignored `.local/uploads` directory. For any different working-directory or deployment arrangement, configure the same absolute `BARBER_UPLOAD_ROOT` for both apps and operator scripts. Keep uploads outside public directories, protect the directory and grant access only to the application/operator account. Separate deployments will need shared storage or a future adapter.

The operator command `npm run media:cleanup` retries deletion of withdrawn files and removes unreferenced generated image files older than 24 hours. Active referenced files are preserved. The delay protects normal in-flight uploads; failed uploads can leave private orphan files until cleanup. Run against the matching database and upload root. No cleanup command or scheduler has been executed or installed here.

## Backups and current limitations

Database backup scripts do not include image files. Stop app writes while taking a database dump and a protected copy of the matching upload directory, then retain and restore them as a pair. Existing backups may contain withdrawn photos; account for those copies in retention/deletion procedures. Browser downloads made before withdrawal cannot be revoked.

Cloud storage adapters, gallery ordering controls and advanced page templates remain future work. See [implementation status](implementation.md) for verification.
