# Client accounts and public booking

The Client App now has shop-specific booking, login, registration, recovery and account routes under `/{shopSlug}`. Unknown, unpublished, suspended and deleted shops are rejected on the server. The application does not expose a shop directory. Publication remains gated until the mandatory publication fields are agreed and the publishing workflow is connected.

Both apps use the shared server-only database repositories. Availability, policy checks, schedule expansion and appointment persistence are reused; the Client App does not have a separate booking engine. The applications currently connect to the same PostgreSQL instance. The previously proposed single-domain gateway and centralized HTTP API remain a routing decision; these changes do not silently deploy that proposal.

Clients register with name, international phone and password, with optional email and birthday. Phones are unique within a shop. Registration does not claim a pre-existing staff-created client profile: the shop must verify the client and issue a one-time setup/recovery code. The owner issues that code from the client profile page, confirms identity verification, and manually gives it to the client. Codes expire after 15 minutes, are stored only as hashes, replace prior codes, and can be used once. Resetting a password revokes that client's sessions. No password is disclosed to staff and no SMS/WhatsApp API is used.

Client sessions use random tokens stored as hashes, scoped to a shop with separate HttpOnly cookies. Sessions expire after eight hours and after one hour of inactivity. Authentication and recovery have database-backed attempt limits. All client writes verify the configured request origin and repeat authorization inside a locked shop transaction. Client security and booking events use `client_events`; owner-assisted recovery is recorded in the existing staff audit log.

Public booking supports multiple services, a specific or any available barber, authoritative slot/pricing revalidation, automatic/manual approval and guest bookings. Guests retain a booking reference and contact the shop for changes; they are never merged into an account based on a phone match. Account holders can see paginated upcoming appointments/history, cancel within the saved deadline and edit their name, email and birthday. Clients can also manage their own consent-aware profile/haircut photos; see [local media](media.md). Phone changes and rescheduling are not connected yet.

Configure `apps/client/.env.local` from its `.env.example`, using the same database as the Business App and `APP_ORIGIN=http://localhost:3002`. Apply all migrations with `npm run db:deploy` once the development database is available. Recent implementation was deliberately not tested or built at the user's request; earlier passing checks do not verify these new flows.
