# Password storage foundation

Node server code imports `hashPassword`, `verifyPassword`, `verifyAccountPassword` and `PasswordCapacityError` from `@barber/auth/password`. This entry uses `server-only` to prevent accidental import into Next.js client components. It is deliberately separate from the authorization helpers. Tests access the internal primitive directly; application code must use the public entry.

The implementation uses asynchronous Node scrypt with N=131072, r=8, p=1, a random 16-byte salt and a 32-byte derived key. This follows the [OWASP scrypt baseline](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) using [Node's built-in crypto API](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback), with no external service or additional crypto dependency. Each operation needs approximately 128 MiB of working memory, with a 160 MiB per-operation ceiling.

All three operations share a limit of two active scrypt jobs per loaded server module instance. Excess work rejects immediately with `PasswordCapacityError`; there is no queue retaining password inputs. Capacity is released on success or failure. Future endpoints must translate this into a generic temporary-unavailability response, not an incorrect-password response. This is a resource safeguard, not per-account/IP rate limiting. Multiple processes, workers or separately bundled module copies each have their own limit; deployment must budget total memory accordingly.

Store the entire returned versioned string in the existing password hash column. Never return hashes in account responses or log passwords/hashes. Verification accepts only the exact supported version, parameters and canonical encoding, so stored data cannot select arbitrary work factors. Comparisons use `timingSafeEqual`; malformed records return false, while crypto operational failures propagate. Future parameter changes require an explicit version migration and compatibility verifier.

Inputs retain spaces, case and Unicode exactly. Empty strings, malformed Unicode and values exceeding 1024 UTF-8 bytes are rejected without truncation. This is a resource/input bound, not a complete account password-strength policy. Registration policy remains to be implemented.

For login orchestration, use `verifyAccountPassword(password, storedHashOrNull)` after a trusted tenant-scoped account lookup. Valid password inputs trigger one scrypt derivation whether the account exists, is missing, or has a malformed/unsupported hash. Missing/malformed records always return false. Dummy values are public constants, never usable credentials. Input validation still rejects invalid passwords before hashing, independent of account existence. `verifyPassword` remains the strict low-level verifier and returns false immediately for malformed stored hashes.

No account creation, login, reset, session or database write is introduced. Before connecting these helpers, implement tenant-scoped phone lookup/normalization, password policy, rate limiting, generic login errors, secure sessions and audited staff-assisted recovery. Equivalent hashing work reduces one source of account enumeration but does not equalize database access or the rest of an endpoint. Staff must never see existing passwords. Recovery must replace the hash through a secure reset workflow.

Run `npm test` for real hashing tests covering independent salts, exact Unicode matching, tampering, malformed records, fixed cost parameters, input bounds and missing-account verification. Deterministic work-limit tests verify overload rejection without queueing and capacity recovery after synchronous/asynchronous errors; integration tests ensure every hashing path uses the shared limit. No database or paid service is required.
